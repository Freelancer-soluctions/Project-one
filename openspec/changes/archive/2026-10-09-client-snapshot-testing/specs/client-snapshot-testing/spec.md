# Spec Delta

## Purpose

Define la política, la configuración y el alcance de snapshot testing en `apps/client`: dónde se permiten snapshots (UI presentacional y estable), con qué matcher (inline vs `.snap` externo), cómo se garantiza la determinismidad y qué invariantes de CI impiden que un snapshot se apruebe sin revisión. Cierra el gap P3 de `docs/learning/unit-tests-enterprise.md` (0 snapshots) de forma limitada y auditable. El alcance cubre **todos** los componentes de `apps/client` que necesiten snapshot testing, determinado por una auditoría de candidatura que clasifica cada directorio del workspace (matriz de cobertura más abajo); ningún directorio se omite en silencio.

## ADDED Requirements

### Requirement: Snapshot configuration is declared in the client Vitest config

`apps/client/vitest.config.js` SHALL declare `test.snapshotFormat` with a bounded output size (`maxOutputLength: 10000`) and `test.update` resolved explicitly from the environment: `'none'` when `process.env.CI` is truthy, `'new'` otherwise. No other Vitest config file SHALL enable snapshot writes.

#### Scenario: Local run creates missing snapshots only

- **WHEN** a developer runs the test suite locally (no `CI` env var) and a snapshot test has no stored reference
- **THEN** the run creates the missing snapshot and passes, and it does not modify or delete existing snapshots

#### Scenario: CI run never writes snapshots

- **WHEN** the test suite runs with `process.env.CI` truthy
- **THEN** `test.update` resolves to `'none'`, no snapshot file is written or deleted, and the run fails on a missing, mismatched, or obsolete snapshot

#### Scenario: The output budget does not truncate reviewed snapshots

- **WHEN** before phase F2 a throwaway component that serializes to more than 10000 characters is rendered through a snapshot test
- **THEN** the produced snapshot contains no truncation or collapse marker; if it does, the budget SHALL be raised (e.g. `maxOutputLength: 100000`) and re-verified before any real snapshot lands

### Requirement: Snapshot update scripts are local-only and CI scripts never update

`apps/client/package.json` SHALL define `test:snapshot` (runs Vitest with `--update=new`, creating only missing snapshots) and `test:snapshot:refresh` (runs Vitest with `-u`, refreshing changed and obsolete snapshots). No script consumed by CI (`test`, `test:unit`, `test:integration`, `test:changed`, `test:changed:ci`, `test:coverage`, `test:coverage:ci`) SHALL pass `-u`, `--update`, `--update=all` or `--update=new`.

#### Scenario: Developer creates a new snapshot locally

- **WHEN** a developer runs `npm run test:snapshot` in `apps/client` after adding a snapshot assertion
- **THEN** only missing snapshots are created; existing changed or obsolete snapshots are left untouched

#### Scenario: Developer refreshes snapshots after an expected UI change

- **WHEN** a developer runs `npm run test:snapshot:refresh` locally and reviews the resulting diff before committing
- **THEN** changed and obsolete snapshots are updated, and the update does not happen in any CI-executed script

#### Scenario: CI scripts remain snapshot-read-only

- **WHEN** `npm run test:changed:ci` or `npm run test:coverage:ci` executes in CI
- **THEN** neither script passes an update flag, so a snapshot diff can only land through a locally reviewed change committed in the PR

### Requirement: Snapshot tests run in the CI prebuild testing substage

The snapshot suite SHALL run inside the existing STAGE 2 PRE-BUILD testing substage of `.github/workflows/ci.yml` — job `test-unit-client` (SUBSTAGE 2D, aggregated by `prebuild-unit-tests-complete`) — through the scripts that job already invokes: `test:changed:ci` for the diff-scoped run and `test:coverage:ci` for the full-suite run. No separate snapshot job SHALL be added, no job SHALL be added to or removed from any `prebuild-*-complete` aggregator's `needs`, and no CI step or CI-consumed script SHALL pass `-u`, `--update`, `--update=all` or `--update=new`. Because GitHub Actions exports `CI=true`, `test.update` resolves to `'none'` in those runs, so the committed `.snap` files and inline snapshots are validated and a missing, mismatched, or obsolete snapshot fails the Vitest step without writing anything.

#### Scenario: A snapshot mismatch fails the prebuild test job

- **WHEN** a PR changes rendered markup without refreshing the corresponding snapshots
- **THEN** `test-unit-client` runs the affected `*.ui.test.jsx`, the Vitest step exits non-zero with the snapshot diff in the log and in `reports/junit.xml`, and no snapshot file is modified (the job's FASE-1 `continue-on-error` controls merge-blocking and is governed by the pipeline's calibration, not by this capability)

#### Scenario: A diff-scoped run still validates committed snapshots

- **WHEN** the TIA scope resolves to `changed` and the diff includes snapshot tests, their components, or only snapshot artifacts (`.snap` or inline edits)
- **THEN** Vitest selects the tests whose module graph intersects the changed files and validates them against the committed snapshots under `update: 'none'`; when the diff selects 0 tests, the existing guard falls back to the full suite, so committed snapshots are never skipped silently

#### Scenario: A shared-path change validates the whole snapshot suite

- **WHEN** `repo-discovery` reports `shared == 'true'` (root manifest, lockfile, workflows) or `origin/main` is not resolvable
- **THEN** the job runs the full client suite with `test:coverage:ci`, executing all snapshot tests (F1 = 37, F2 = 20, F3 = 26 files) under `update: 'none'`

#### Scenario: CI cannot approve a snapshot

- **WHEN** the workflow steps and npm scripts reachable from `test-unit-client` are inspected
- **THEN** neither `ci.yml` nor `test`, `test:unit`, `test:integration`, `test:changed`, `test:changed:ci`, `test:coverage`, `test:coverage:ci` contains an update flag, so a snapshot can only change through a locally reviewed run committed in the PR

#### Scenario: The prebuild stage order and aggregator contracts are preserved

- **WHEN** the snapshot wiring is verified against `.github/workflows/ci.yml`
- **THEN** snapshot execution happens in the existing prebuild job (order: prebuild → build → artifact unchanged), `prebuild-unit-tests-complete.needs` still contains exactly `[test-unit-client, test-unit-server, test-integration, test-smoke, client-coverage, server-coverage]`, and no job id or display name bound to the ruleset is renamed

#### Scenario: CI runs are deterministic for snapshots

- **WHEN** the suite runs on the CI runner (`CI=true`)
- **THEN** execution stays deterministic — `maxWorkers: 1` from the `CI` branch of `vitest.config.js`, `pool: 'forks'` with default isolation, fixtures frozen per test, `vi.setSystemTime` for dates, i18n fixed to `'en'` and per-test MSW handlers — so the same committed snapshots pass on every run

### Requirement: Snapshot tests live in `*.ui.test.jsx` files with deterministic inputs

Snapshot tests SHALL be written in `*.ui.test.jsx` files (already matched by the existing `include` globs), SHALL render through the project's test utilities with i18n fixed to `en`, and SHALL use only deterministic inputs: fixed fixture data, `vi.setSystemTime`/fake timers for any date, property matchers or normalization for `uuid`/`Math.random`, and per-test MSW handlers (`server.use(...)`) for network data. Fixtures SHALL be local to the test, never shared mutable globals.

#### Scenario: A snapshot containing a date is stable across runs

- **WHEN** a component renders a date and the test freezes system time (e.g. `2026-01-01T00:00:00Z`) before rendering
- **THEN** repeated runs produce byte-identical snapshots regardless of the execution date or locale

#### Scenario: A snapshot depending on network data is stable across runs

- **WHEN** a component fetches data and the test overrides the MSW handler with a fixed fixture inside the test
- **THEN** the snapshot reflects only the fixture and does not vary with handler order or timing

#### Scenario: A test file uses the UI test suffix

- **WHEN** a snapshot assertion is added for a client component
- **THEN** it lives in a file matching `src/**/*.ui.test.jsx` so Vitest collects it with the existing configuration

### Requirement: The F1 set of 37 small presentational files uses inline snapshots

The F1 set — exactly 37 files: the 29 `components/ui/*` shadcn primitives, `components/loader/Loader`, `components/loader/Spinner`, `components/layout/Header`, `components/layout/Footer`, `components/layout/Main`, `components/layout/index`, `components/404/NotFound`, `components/500/InternalServerError` — SHALL be covered with `toMatchInlineSnapshot` on a component or subtree, with a descriptive hint instead of a positional index. Each snapshot SHOULD stay at or below ~50 lines of serialized markup (non-normative guidance; the normative rule is one component/subtree per matcher). For composite primitives (`form`, `command`, `dropdown-menu`, `select`, `calendar`) only the field/trigger subtree SHALL be snapshotted, never an open animated menu; `calendar` SHALL use a fixed date fixture.

#### Scenario: A shadcn primitive gets an inline snapshot

- **WHEN** a snapshot test renders a `components/ui/*` primitive with fixed props
- **THEN** the serialized DOM appears as a string literal inside the same `*.ui.test.jsx` file, tagged with a descriptive hint, and no `__snapshots__` file is created for it

#### Scenario: A design-system class change is caught in review

- **WHEN** a token or `tailwind-merge` change alters the classes of a covered primitive
- **THEN** the local test run fails with an inline diff in the test file, and the reviewer sees that diff in the PR

### Requirement: The F2 set of 20 Datatable components uses external `.snap` snapshots over frozen fixtures

The F2 set — exactly 20 non-empty `modules/**/components/*Datatable.jsx` files (21 such files exist; `modules/providerOrder/components/ClientOrderDatatable.jsx` is a 0-line empty file handled as dead code in tasks before F2) — SHALL be covered with `toMatchSnapshot` stored under `__snapshots__/`, each rendering exactly 3 fixed fixture rows, with frozen system time for date columns and local MSW handlers for linked data. Each individual snapshot SHOULD stay under ~100 lines (non-normative guidance); larger structures SHALL be segmented to the table subtree.

#### Scenario: A Datatable renders a frozen three-row fixture

- **WHEN** a Datatable snapshot test renders with a fixed 3-row fixture and frozen time
- **THEN** the run generates a `.snap` entry under ~100 lines that is byte-stable between runs

#### Scenario: A column or cell change fails the snapshot

- **WHEN** a refactor alters a rendered column header, cell value, tooltip or pagination control of a covered Datatable
- **THEN** the test fails and shows the diff between the stored `.snap` and the new markup

#### Scenario: The two `ClientOrderDatatable.jsx` files are not confused

- **WHEN** a Datatable snapshot test is created for a `ClientOrderDatatable`
- **THEN** the test targets `modules/clientOrder/components/ClientOrderDatatable.jsx`; `modules/providerOrder/components/ClientOrderDatatable.jsx` is the empty dead file and SHALL NOT be snapshotted

### Requirement: The F3 set of 26 remaining presentational components uses inline snapshots

The F3 set — exactly 26 files: `components/PaginationControls`, `components/alertDialog/AlertDialog`, `components/backDash/BackDashBoard`, `components/dataTable/DebouncedInput`, `components/dataTable/Filter`, `components/dataTable/Pagination`, `components/dataTable/cellWithTooltip`, `components/favoriteToggle/favoriteToggle`, `components/quickAccess/QuickAccess`, `components/tiptap/MentionList`, `modules/auth/components/AuthFooter`, `modules/auth/components/AuthWelcomeMessage`, `modules/events/components/AttendeeStatus`, `modules/events/components/EventFiltersForm`, `modules/events/components/EventList`, `modules/home/components/AccessCardModules`, `modules/home/components/EventCalendarWidget`, `modules/home/components/Navbar`, `modules/home/components/NotesSummary`, `modules/home/components/SideBar`, `modules/home/components/StockSummary`, `modules/notes/components/NotesCard`, `modules/notes/components/NotesColumn`, `modules/settings/components/SettingsLanguage`, `modules/settings/components/SettingsProduct`, `modules/settings/components/SettingsWsStatus` — SHALL be covered with `toMatchInlineSnapshot` with props, fixtures, frozen time and local MSW handlers fixed inside each test. The last 11 files are the delta added by the expanded audit of `apps/client` and the round-2 re-review: `alertDialog/AlertDialog`, `backDash/BackDashBoard`, `favoriteToggle/favoriteToggle`, `dataTable/Pagination`, `home/AccessCardModules`, `home/NotesSummary`, `home/StockSummary`, `events/EventList` (expanded audit), plus `home/SideBar` (Redux only dispatches `logout`; render inputs are props — `displaySettings`, `dataCountStock`, i18n `en`, `MentionCountContext` default; wrapped in `MemoryRouter` + a minimal Redux `Provider` store), `notes/NotesCard` (dialogs render closed with `open={false}`, dates come from the note prop fixture, `useSocket` inert without a token, mutations fire only on click; wrapped in a store provider), and `tiptap/MentionList` (prop-driven popup, 95 lines, fixture of 3 mentions, existing RTL test stays).

#### Scenario: A pure component gets a fixture-backed inline snapshot

- **WHEN** an F3 component renders from props that the test fixes in a local fixture (frozen date, fixed MSW response)
- **THEN** the inline snapshot is byte-stable across runs and no unfrozen `Date` value reaches the serialized output

#### Scenario: A directory outside the matrix must be classified first

- **WHEN** a new directory containing UI components appears under `apps/client` (a new module, a new `src/components/*` folder, or a new non-`src` directory)
- **THEN** it is added to the matrix and classified (candidate for F1-F3 or excluded with an explicit reason) before any snapshot test for it is merged

#### Scenario: Candidate totals stay reconciled across artifacts

- **WHEN** the candidate counts are read from `proposal.md`, `design.md`, this spec and `tasks.md`
- **THEN** all four agree on F1 = 37, F2 = 20, F3 = 26 and total = 83 candidate files

### Requirement: Container and dynamic surfaces are excluded from snapshot testing

Snapshot matchers SHALL NOT be used on `pages/*` containers, `App.jsx`/`main.jsx`, `*Dialog.jsx` or `*FiltersForm.jsx` components backed by react-hook-form/zod (sole exception: `modules/events/components/EventFiltersForm.jsx`, which has no RHF and is snapshotted subtree-only), interactive forms with validation state regardless of library (sole example: `modules/settingsProductCategories/components/SettingsProductsCategoryForm.jsx`, verified non-RHF yet still excluded as an interactive form with validation state), route guards, tiptap editors whose render depends on a live tiptap `Editor` instance (`TiptapEditor`, `MenuBar`), components whose rendered markup is derived from Redux store state (a component that only _dispatches_ from Redux while rendering from props — e.g. `SideBar` — is a candidate, not excluded), providers, or any component whose rendered content depends on `Date.now()`, `new Date()`, `toLocaleString()`, `Math.random()` or `uuid` without being frozen first. Because `vi.setSystemTime` freezes `new Date()`, size and review-value — never determinism — are the only valid grounds for the remaining exclusions (they are recorded as such in the matrix). Those surfaces SHALL continue to be validated with explicit RTL assertions (`getByRole`, `getByText`, `userEvent`).

#### Scenario: A form dialog is covered by assertions, not snapshots

- **WHEN** a reviewer encounters a snapshot assertion added inside a `*Dialog.jsx` or `*FiltersForm.jsx` test
- **THEN** the change is rejected in favor of explicit role/text assertions, because input ids, validation messages and touched/dirty state are unstable across refactors

#### Scenario: An unfrozen date in a snapshot is rejected

- **WHEN** a snapshot test renders live `Date.now()`/`toLocaleString()` output without fake timers
- **THEN** it is treated as a defect: the test must freeze or normalize the value before the snapshot can be committed

### Requirement: Snapshot artifacts are committed and reviewed like code

Every generated `.snap` file and inline snapshot SHALL be committed in the same PR as the code that produced it, and SHALL be committed before the branch is pushed. Before committing an update, the developer SHALL run it locally (`test:snapshot` or `test:snapshot:refresh`) and review the `git diff`. Obsolete snapshots (from renamed or deleted tests) SHALL be cleaned up locally and the deletion committed; they MUST fail CI otherwise. The PR review checklist SHALL verify: single component/subtree, frozen dates/uuids, diff under ~100 lines (non-normative guidance), expected (not incidental) markup, no update run in CI, no obsolete entries, and every snapshot created locally is committed before push.

#### Scenario: A snapshot update lands through review

- **WHEN** a developer refreshes snapshots after an intended UI change and opens a PR
- **THEN** the PR contains both the source change and the snapshot diff, and a reviewer can judge the UI change from the diff alone

#### Scenario: A renamed test leaves an obsolete snapshot

- **WHEN** a snapshot test is renamed or deleted without refreshing snapshots locally
- **THEN** CI fails on the obsolete snapshot until the developer refreshes locally and commits the removal

#### Scenario: Snapshots created locally are committed before push

- **WHEN** a local run with `update: 'new'` creates missing snapshot files and the developer pushes without committing them
- **THEN** CI fails on the missing snapshots (`update: 'none'` rejects them), so every locally created or updated snapshot SHALL be committed and pushed together with its test

### Requirement: Snapshot coverage gap is tracked in the testing metrics

When phase F1 (primitivas shadcn + layout/errores) completes, the snapshot metric in `docs/learning/unit-tests-enterprise.md` SHALL be updated from "0 snapshots" to the actual count of committed snapshots, and `docs/code-review-checklist.md` SHALL include the snapshot review checklist, linking `docs/learning/snapshot-testing.md` as the reference doc.

#### Scenario: The P3 gap is closed

- **WHEN** F1 tests are green locally and in CI without update flags
- **THEN** `docs/learning/unit-tests-enterprise.md` reports a non-zero snapshot count instead of the P3 "0 snapshots" entry
