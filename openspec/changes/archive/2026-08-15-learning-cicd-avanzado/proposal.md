## Why

Un Junior que completó los niveles Fundamentos (00-04) e Intermedio (05-10) ya domina CI: lee y modifica cualquier workflow de `.github/workflows/`, entiende jobs, caches, composite actions y hooks de Husky. Pero la mitad "CD" del acrónimo sigue siendo una caja negra: el proyecto tiene una pipeline de despliegue real a AWS (ECS Fargate + ECR + RDS + ALB) orquestada por `deploy.yml`, un sistema de preview environments en PR (`preview.yml`), autenticación GitHub→AWS sin credenciales estáticas vía OIDC, y un flujo de releases con Changesets (`release.yml`). La documentación existente (`docs/aws-deploy-architecture.md`, `docs/aws-cd-learning-path.md`, `docs/aws-dev-local-floci.md`, `docs/aws-learning-with-floci.md`) es de referencia técnica y asume conocimientos previos de AWS; sin una guía didáctica el lector se atasca justo en los temas más complejos del sistema CI/CD del proyecto: AWS, OIDC y despliegue. Sin este nivel no se cumple el objetivo de la ruta: **"puedo explicar y operar el despliegue completo del proyecto, del push a producción, sin credenciales reales de AWS"**.

## What Changes

- Crear el nivel **Avanzado** de la ruta de aprendizaje incremental de CI/CD en `docs/learning/ci-cd/`, continuando la numeración del nivel Intermedio (05-10) con las guías 11-17.
- `avanzado-README.md`: índice del nivel Avanzado (archivo separado, estructura modular como en los niveles previos), con objetivos del nivel, prerequisitos ("completado Fundamentos + Intermedio"), mapa de navegación 11-17 y enlace de vuelta a Intermedio.
- `11-cd-conceptos-aws.md`: conceptos CD desde cero (CI vs CD, estrategias de despliegue blue-green y canary) e inventario de servicios AWS del proyecto: ECS Fargate, ECR, RDS PostgreSQL, IAM OIDC, ALB (sticky sessions para Socket.IO), VPC y Secrets Manager. Incluye el diagrama mermaid de componentes de `docs/aws-deploy-architecture.md`.
- `12-floci-emulador-aws.md`: qué es Floci (MIT, 68 servicios, puerto 4566, imagen ~90MB, arranque ~24ms), tabla comparativa vs LocalStack, por qué Floci (cero costo cloud para aprendizaje/CI), el stack `docker-compose.preview.yml`, comandos hands-on (`docker compose up -d floci`, healthcheck, env vars con credenciales dummy `AWS_ACCESS_KEY_ID=test`, `AWS_ENDPOINT_URL=http://localhost:4566`) y el patrón del script `preview-smoke.mjs`. Secuencia pedagógica Floci → Consola → Terraform (de `docs/aws-cd-learning-path.md`).
- `13-deploy-yml-walkthrough.md`: walkthrough profundo de `.github/workflows/deploy.yml`: Fase 1 (docker-build con Floci + Postgres efímera + smoke tests) → Fase 2 (ecr-push, deploy-staging, deploy-production con aprobación manual). Gating con `vars.AWS_ROLE_ARN != ''`, jobs skipped con `::notice::` visibles en UI para el learning path de Fase 1, inventario de secrets (vars.AWS*ROLE_ARN, secrets.STAGING*\_, secrets.PROD\_\_), el gotcha del ARN legacy `JWT_SECRET` vs env var `SECRETKEY`, y concurrency groups por entorno (sin cancel-in-progress).
- `14-preview-environments-yml.md`: walkthrough de `.github/workflows/preview.yml`: triggers (pull_request opened/reopened/synchronize + workflow_dispatch), services (Floci + Postgres efímera), build de imagen Docker del server, Prisma migrate, arranque del contenedor, health check, smoke tests contra Floci, captura de URL de preview Vercel vía commit status API y comentario en PR con marker `<!-- preview-environments -->`. Concurrency `preview-${{ github.event.pull_request.number }}` con cancel-in-progress:true.
- `15-oidc-sin-credenciales-estaticas.md`: OpenID Connect a fondo: por qué OIDC en lugar de access keys de larga duración (rotación, blast radius, auditoría), cómo funciona (GitHub firma un JWT → la trust policy IAM verifica → STS assume-role-with-web-identity → credenciales temporales), trust policy StringLike `repo:owner/repo:*` + filter de environment en GitHub Environments (no en trust policy), y política de mínimo privilegio (ECR push/pull, ECS update/describe solo en clusters del proyecto).
- `16-ecs-circuit-breaker-health-checks.md`: mecánica de despliegue ECS: registro de task definition (pineada por Git SHA), `aws ecs update-service --force-new-deployment`, `deploymentCircuitBreaker={enable:true,rollback:true}` con rollback automático si fallan los health checks, config de health check (interval 30s, timeout 5s, retries 3, startPeriod 60s, path /health) y smoke tests remotos post-deploy (staging 5 min, prod 5 min — 30 retries × 10s ambas). Por qué este patrón es "production-grade" vs un deploy naïve.
- `17-changesets-release-yml.md`: walkthrough de `.github/workflows/release.yml`: push a main → detectar changesets pendientes → abrir PR "chore: version packages" → merge → publish a npm + tags git. `fetch-depth: 0` requerido (changesets necesita el historial de commits). Estructura del directorio `.changeset/`. Referencia: spec existente `openspec/specs/release-workflow/spec.md`.
- **No se modifica código de aplicación ni workflows**: es documentación didáctica nueva. No se duplica `docs/aws-*.md`, `docs/cicd-estado-actual.md` (sección 10) ni `docs/workflows-mantenimiento-guia.md` (sección 14) — se enlazan (link, no copy), con snippets cortos citando la ruta fuente.
