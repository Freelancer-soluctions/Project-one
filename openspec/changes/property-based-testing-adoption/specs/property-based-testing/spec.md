# Spec Delta — property-based-testing

## Purpose

Adopt property-based testing (fast-check) en el monorepo: dependencias instaladas en los
workspaces, properties deterministas con presupuesto de tiempo acotado, wiring CI advisory
en STAGE 2 PRE-Build y corrección lockstep de la documentación que hoy afirma un estado
desactualizado de la instalación.

## ADDED Requirements

### Requirement: PBT dependencies installed per-workspace

The `apps/server` and `apps/client` workspaces SHALL declare `fast-check@4.x` as a
`devDependency` of their own `package.json`, and no additional PBT helper package
(`@fast-check/vitest`, `zod-fast-check`) SHALL be introduced; the root manifest SHALL NOT
declare any `fast-check` package (avoiding the phantom dependency purged in commit
`9ae16e8f`), while the root `test:pbt` script SHALL only delegate to workspaces with
`--workspaces --if-present`.

#### Scenario: workspace-local installation

- **WHEN** a developer runs `npm ls fast-check` from `apps/server` or `apps/client`
- **THEN** fast-check resolves from the workspace's own `devDependencies` (no phantom dep)
- **AND** `npm ls fast-check` from the repo root reports it only as a transitive/workspace
  entry, not as a root manifest dependency
- **AND** `grep -E '"(@fast-check/vitest|zod-fast-check)"' apps/*/package.json` reports 0
  matches (zod arbitraries are hand-written — see initial property coverage)

#### Scenario: delegation script

- **WHEN** a developer runs `npm run test:pbt` at the repo root
- **THEN** it delegates to every workspace that defines `test:pbt` and does not fail on
  workspaces that do not

### Requirement: Deterministic global PBT configuration

Each workspace's Vitest setup file SHALL configure fast-check globally so that `numRuns` is
1000 and `seed` is fixed (42) when `process.env.CI` is truthy, and `numRuns` is 100 with a
random seed otherwise; no individual property SHALL override these environment defaults
inline. That configuration SHALL take effect in every Vitest config variant used by test
jobs — the regular `vitest.config.js` and the scoped/TIA variants that must inherit its
`test.setupFiles` — so `configureGlobal` never applies silently in one variant only.

#### Scenario: CI run is reproducible

- **WHEN** a property fails in CI (where `CI=true`)
- **THEN** the failure output contains the counterexample together with the `seed` and
  `path` needed to replay it
- **AND** a developer reproduces the same counterexample locally by passing
  `{ seed, path, endOnFailure: true }` to `fc.assert` (or by temporarily calling
  `fc.configureGlobal({ seed, path })` in the setup file) — never through Vitest CLI
  flags, which Vitest 4.1.11 does not provide (`--seed`/`--path` are not valid flags)

#### Scenario: local run explores new inputs

- **WHEN** a developer runs `test:pbt` locally without `CI` set
- **THEN** each run uses a random seed and 100 runs per property

### Requirement: Initial property coverage of domain invariants

The first property suites SHALL cover: (a) server Joi validators through a Joi-driven
arbitrary that parses generated candidates so properties evaluate on domain-valid values,
(b) pure-logic laws (sorting: order/permutation/idempotency; pagination: union equals input
without overlap), (c) domain invariants (stock never negative, attendance check-in/out
idempotent), (d) monetary calculations using `fc.bigInt` minor units (never floating point),
and (e) client zod schemas round-tripped through hand-written arbitraries built with
`fc.record`/`fc.letrec` that mirror the 22 schema shapes (`safeParse` succeeds on
generated inputs). Property test files SHALL follow the existing `*.unit.test.js(x)` naming
so they are collected by the current Vitest globs and travel with TIA changed-only selection.

#### Scenario: Joi-driven property (server)

- **WHEN** the server PBT suite runs
- **THEN** every generated value fed to a Joi-validated predicate has already been parsed by
  that schema (validate with `convert`/`stripUnknown`), and the predicate asserts
  `schema.validate(value).error` is undefined

#### Scenario: monetary property uses bigInt

- **WHEN** a monetary property runs
- **THEN** inputs are `fc.bigInt` minor units — no `fc.double()` — so failures indicate a
  real bug, not floating-point noise (no flaky property from precision)

#### Scenario: zod round-trip (client)

- **WHEN** the client PBT suite runs
- **THEN** values generated by the hand-written arbitrary (`fc.record`/`fc.letrec` mirroring
  the target schema shape) always satisfy `schema.safeParse(value).success === true`

#### Scenario: property suites are discovered by existing runners

- **WHEN** `npm run test:unit` (or `test:pbt`) runs in either workspace
- **THEN** the new `*.unit.test.*` property files are included by the existing include globs
  with no separate config

### Requirement: Quality standards for properties

Each property SHALL be strong (would fail on a plausible bug — tautologies like
`x === x` are forbidden), SHALL NOT mutate its inputs inside the predicate (clone first),
SHALL prefer arbitrary constraints (`min`/`max`/`minLength`) over `.filter`, and SHALL let
exceptions propagate (no `try/catch` returning `true`). Anti-patterns from the research doc
§4.5 (weak properties, filter-heavy generators, huge `numRuns`, missing seed logging, PBT
for mock-heavy CRUD) SHALL be rejected in review.

#### Scenario: weak property rejected

- **WHEN** a review encounters a property whose predicate is always true (e.g.
  `expect(x).toEqual(x)` on a trivially reflexive relation)
- **THEN** it is rejected or rewritten so that introducing a plausible bug makes it fail

#### Scenario: exception propagates for shrinking

- **WHEN** a predicate throws on a generated input
- **THEN** the error propagates to the runner (no catch-all wrapper) so the shrinker
  converges on the minimal counterexample

### Requirement: Advisory CI job within the prebuild budget

CI SHALL run the PBT suites as an advisory job in STAGE 2 PRE-Build, defined inside the
unit-testing substage block (SUBSTAGE 2D) with `continue-on-error: true` (FASE 1 pattern),
the display name `Tests: Property Tests` required by the block-naming convention, a fixed
seed, and a total wall-time budget under 1-2 minutes. The job SHALL NOT be listed in any
job's `needs`, preserving `prebuild-unit-tests-complete`'s contract of exactly the 6
declared needs (`test-unit-client`, `test-unit-server`, `test-integration`, `test-smoke`,
`client-coverage`, `server-coverage`), and SHALL NOT alter any existing job's
`continue-on-error`, TIA selection, ordering, or sharding behavior (owned by
`ci-testing-gate-promotion`, `ci-test-impact-analysis`, `smart-test-ordering`,
`test-sharding`).

#### Scenario: PBT job is advisory

- **WHEN** a property fails on a pull request
- **THEN** the job reports the full counterexample log (seed/path, untruncated) but does
  not block `prebuild-unit-tests-complete` or `ci-complete`

#### Scenario: aggregator contract preserved

- **WHEN** the change is applied and CI runs
- **THEN** `prebuild-unit-tests-complete.needs` still contains exactly the 6 original job
  ids
- **AND** `property-tests` appears in no job's `needs` — its result reaches the PR as its
  own advisory check, never as a seventh aggregator input

#### Scenario: budget respected

- **WHEN** the PBT job runs in CI with `numRuns: 1000`
- **THEN** it completes within the 1-2 minute budget; if a property exceeds it, `numRuns`
  is reduced or the property split — never left blocking the pipeline

### Requirement: Flaky properties quarantined, never silently retried

A non-deterministic (flaky) property SHALL be diagnosed (non-deterministic input, input
mutation, over-strict `filter`, clock/network/order dependence) and fixed, or quarantined
through the same `vitest-flaky-reporter.mjs` + quarantine path used for flaky tests;
silent retry of a failing property SHALL be prohibited.

#### Scenario: flaky property handled by quarantine path

- **WHEN** the same property fails intermittently with different seeds
- **THEN** it is either fixed at the root cause or moved to quarantine with an issue — it
  is never masked by a retry policy

### Requirement: Documentation lockstep with actual PBT state

After installation, `docs/learning/unit-tests-enterprise.md` (§23.3 and its summary table)
and `docs/learning/panorama-resumen.md` SHALL state the real state (fast-check 4.x installed
in workspaces, first properties present) instead of the outdated
"`fast-check@3.23.2` instalado, 0 usos" claim.

#### Scenario: docs match reality

- **WHEN** a developer reads the gap tables in those two documents after the change
- **THEN** the fast-check version, install location and usage count match what
  `npm ls fast-check` and a `grep fc.property` over the repo actually report
