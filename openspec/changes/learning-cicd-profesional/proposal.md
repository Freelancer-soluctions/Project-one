## Why

Un desarrollador que completó los niveles Fundamentos (00-04), Intermedio (05-10) y Avanzado (11-17) ya sabe escribir y modificar workflows, dominar Husky, composite actions, caching, y desplegar a AWS con Floci + ECS + OIDC + Changesets. Pero **todavía no piensa como dueño de un pipeline de producción**: no conoce la familia SAST/SCA/SBOM en profundidad, no gestiona Dependabot de forma rutinaria, no tiene una filosofía de mantenimiento de workflows ("el código se pudre"), y no conoce los marcos que separan a un Senior de un Staff (DORA, SLSA, VEX). La documentación técnica existente (`docs/cicd-estado-actual.md` Stage 4/6, `docs/cicd-plan-implementacion.md` §12 DORA/SLSA/VEX, `docs/workflows-mantenimiento-guia.md`) es de referencia y asume conocimientos; sin este nivel el lector se queda en "puedo operar el CI" y no alcanza el objetivo Staff: **"diseño, aseguro, mido y mantengo el pipeline como un activo de producción"**.

## What Changes

- Crear el nivel **Profesional** (final) de la ruta de aprendizaje incremental de CI/CD en `docs/learning/ci-cd/`, continuando la numeración de los niveles previos (00-04 Fundamentos, 05-10 Intermedio, 11-17 Avanzado) con las guías 18-23.
- `profesional-README.md`: índice del nivel Profesional (archivo separado, siguiendo la convención de `intermedio-README.md`), con objetivos del nivel, prerequisitos ("completado Fundamentos + Intermedio + Avanzado"), mapa de navegación 18-23, y una **sección final de wrap-up/graduación** que conecta los 4 niveles en una ruta de maestría CI/CD coherente (Junior → Staff).
- `18-security-yml-sast-sca-sbom.md`: walkthrough profundo de `.github/workflows/security.yml` (5 jobs: dependency-scan/sast/secrets/sbom/dependency-review). Conceptos de seguridad introducidos **desde cero**: SAST (CodeQL `init@v4` + `analyze@v4`, `languages: javascript,actions`, autobuild comentado → `npm ci` manual por ser monorepo), SCA (Trivy `aquasecurity/trivy-action@0.36.0`, filesystem scan, severidad CRITICAL/HIGH, `exit-code: '1'` fail-closed, SARIF via `codeql-action/upload-sarif@v4`), SBOM (`anchore/sbom-action@v0.24.0`, CycloneDX JSON, artifact 365 días), detección de secrets con Gitleaks (OSS `docker://zricethezav/gitleaks:v8.22.1` + licensed `gitleaks/gitleaks-action@v3` gated por `${{ secrets.GIT_LEAKS }}`), Dependency Review (`actions/dependency-review-action@v5`). Incluye el gotcha del secret opcional GIT_LEAKS (warning + skip silencioso) y la política de permisos: `security-events: write` presente en los workflows que suben SARIF (security.yml + scheduled-security.yml) Y en ci-enterprise.yml (excepción — workflow de referencia no-operacional; notarlo como excepción/violación del 'mínimo privilegio'); security-digest.yml NO lo necesita (sube artifacts, no SARIF).
- `19-scheduled-security-yml.md`: seguridad por cron. `.github/workflows/scheduled-security.yml` (lunes 03:00 UTC, gitleaks full-history `--all` → JSON + SARIF + artifact con `if: always()`) y `.github/workflows/security-digest.yml` (mismo cron, SBOM + OSV Scanner `google/osv-scanner-action@v2.5.0` → digest markdown + comment opcional en PR via input `pull_request_number`). Jobs `notify-failure` (crean issues, `issues: write` solo aquí). Semántica fail-closed (`continue-on-error` removido). **El modelo de seguridad de 3 niveles: pre-commit / PR / cron (shifting left)** como principio organizador central.
- `20-dependabot-3-ecosistemas.md`: Dependabot en profundidad. `.github/dependabot.yml` (auditado agosto 2026): tres ecosistemas — npm (raíz, weekly lunes 03:00 UTC, grupos dev-deps minor/patch), github-actions (weekly, prefix `ci`), docker (`apps/server`, weekly, prefix `ci`). Rutina mensual: revisar cluster de PRs, batch-merge patch+minor, evaluar major aparte, ignore de majors react/react-dom. Diferencia de cadencia npm vs github-actions. Por qué Dependabot evita que el repo se quede con actions stale (problema de drift enumerado en `docs/workflows-mantenimiento-guia.md`).
- `21-mantenimiento-workflows.md`: filosofía de mantenimiento "**los workflows son código y se pudren**". `.nvmrc` como single source of truth — nunca editar `node-version:` workflow por workflow (Caso 1 EBADENGINE con omniroute@3.8.49). `fetch-depth: 0` opt-in, no default (Caso 2 dorny/test-reporter). Política de versionado de actions: tags vs SHA pinning (decisión: tags + Dependabot gana). Gotcha del timeout de bash 120s en pre-commit. Checklist de mantenimiento trimestral (11 items de la sección 17 de `docs/workflows-mantenimiento-guia.md`). Anti-patrones: editar `.nvmrc` workflow por workflow, pins en engines de package.json, `fetch-depth: 0` "por si acaso", combinar bump+workflow en un commit.
- `22-dora-metrics-performance-tuning.md`: métricas DORA en profundidad — Deployment Frequency, Lead Time for Changes, Change Failure Rate, MTTR — y cómo el pipeline afecta cada una. SLSA (Supply-chain Levels for Software Artifacts) niveles 1-4 y dónde se ubica el proyecto (nivel 2-3 vía provenance SBOM + OIDC + dependency review). Performance tuning: jobs paralelos, cache hit ratio, path filtering para saltar trabajo no usado, cancelación por concurrency, composite actions para deduplicar setup, y `act` para dry-run local sin gastar minutos de GitHub Actions.
- `23-ci-enterprise-reference-pipeline.md`: qué separa el CI/CD del proyecto de un pipeline enterprise de referencia. 9 workflows vs 30+ hipotéticos. Requisitos de SLSA Level 3 (provenance firmada, builds hermetic, entornos de build aislados). VEX (Vulnerability Exploitability Exchange) — comunicar si una vuln es explotable. Escaneo de IaC (Terraform en CI) — el gap del proyecto (no hay Terraform aún, pero `docs/aws-deploy-architecture.md` tiene referencia). Pipeline CI enterprise de referencia (`ci-enterprise.yml` — **interno**, paths `frontend/`/`backend/` inexistentes en este monorepo, usado como referencia didáctica de un pipeline de 30+ jobs). Future-proofing: orquestación de contenedores (Kubernetes/EKS), canary deploys, feature flags, OpenTelemetry.
- **No se modifica código de aplicación ni workflows**: es documentación didáctica nueva. No se duplica `docs/cicd-estado-actual.md`, `docs/cicd-plan-implementacion.md`, `docs/workflows-mantenimiento-guia.md` ni `docs/aws-*.md` — se enlazan (link, no copy), con snippets cortos citando la ruta fuente.
